## S1 — `Lexer`

Opened with `Stage1LexerSpec` green at 11/11, and the linearity observation the
spec prints:

```text
[observation] lex 1,000,000 terms, ms = 63
```

63 ms for 4,000,001 characters, against a budget of 60,000. Three questions, all
about design choices rather than about whether the code works.

### 45. The `case _` of the symbol match went from `loop(endId, acc)` to `loop(endId + 1, acc)`. Both are unreachable. If the unreachability ever fails, the first hangs forever and the second drops a character and continues. Which do you prefer in unreachable code, and how would you find out the unreachability had failed?

**Answered partially** — the second was chosen, for two reasons, one right and
one exactly backwards.

Right: *"não vira uma recursão infinita."* It does not, and under `@tailrec` that
matters more than it looks — see the closing note.

Backwards: *"eu consigo pegar nos testes."* Discoverability runs the other way,
and this session is the evidence. The hanging version sat in the working tree
for one round and the suite could not be run at all: no assertion failed, no
stack trace printed, the run had to be killed by hand. That is maximally
annoying and **minimally missable**.

```text
branch                        what the suite does       what it tells you
---------------------------   -----------------------   ----------------------
loop(endId, acc)              never terminates          that something is wrong,
                                                        with no location
loop(endId + 1, acc)          goes green                nothing
Left(UnexpectedChar(c, i))    fails one assertion       the character and the
                                                        index
```

A shorter, well-formed token list is indistinguishable from a correct one unless
a test feeds that exact character *and* asserts the exact list. Silence is worse
than a hang.

**The question was a false choice, and the complete answer is the third row.** A
character reaching that branch is one `isInvalid` approved and `symbolOf` could
not classify — which is the definition of a character the lexer does not know how
to handle, and `UnexpectedChar` is the name the project already has for it. It
costs nothing, it is true to what the situation would mean, and it removes an
asymmetry that survives reachability entirely: **that branch is the only place in
`tokenize` that discards input in silence.** Every other path either produces a
token or produces a `Left`. The discard of trailing separators at
`endSep >= input.size` is in the contract; this one is not.

**The closing note, and it is the transferable part.** `@tailrec` compiles a tail
call to a `goto` (Module 3 §6). The annotation that protects the stack is
therefore also the one that removes the cheapest symptom a non-progressing
recursion has:

```text
                      without @tailrec             with @tailrec
non-progressing   StackOverflowError in ms,    runs forever, no output, no
recursive call    with a stack trace naming    location, and costs a timeout
                  the line                     on every run
```

*Not advancing* is a defect class whose only witness is the clock.

### 46. `isSymbol` and the symbol `match` are two enumerations of the same set, and nothing makes them agree. Add `%` to `isSymbol` and not to the `match`: trace `"1 % 2"`, say where the error surfaces, and say whether the compiler can be made to care.

**The trace was correct.** `MyList(Num(1.0), Num(2.0))` — two operands and no
operator — and `tokenize` returns `Right`:

```text
at   endSep   what happens
--   ------   ------------------------------------------------------------
 0        0   isInvalid('1') false; endNum = 1; Num(1.0); loop(1)
 1        2   isInvalid('%') FALSE, because isSymbol now accepts it
          2   endNum = 2 = endSep, so no number
          2   endId  = 2 = endNum, so no identifier
          2   the match has no case for '%'  ->  case _  ->  loop(3)
 3        4   isInvalid('2') false; endNum = 5; Num(2.0); loop(5)
 5        5   endSep >= size  ->  Right(Num(1.0) :: Num(2.0))
```

**Where it surfaces was the half that was missing, and it is the expensive
half.** Not in Stage 1 — in **Stage 2**:

```text
Parser.parse(Num(1.0) :: Num(2.0))  ->  Left(TrailingInput(Num(2.0), 1))
```

`expr` parses `1` as a complete expression, returns, and the top-level
full-consumption check of guide §17 finds `Num(2.0)` unconsumed. A **lexical**
defect is therefore reported as a **syntactic** one, one stage downstream,
against a *token* index of 1 — which, by guide §10, cannot be converted back to
the character index 2 where the `%` actually sits. The position debt the project
takes on purpose is what makes this particular error un-diagnosable from its
message.

**On making the compiler care**, the answer given — a `Char => Token` converter
plus an `if` guarded by `isSymbol` — is the right instinct and stops one step
short: it **moves** the duplication rather than removing it. Two enumerations
remain, the converter's and `isSymbol`'s, and still nothing makes them agree.

The step that closes it is to make one **derive** from the other, so that there
is one list and no second place to forget:

```scala
private def symbolOf(c: Char): Option[Token]      // the only enumeration
private def isSymbol(c: Char): Boolean = symbolOf(c).isDefined
```

Applied. The compiler does not check the derivation — it cannot, since `Char` is
not a closed ADT and a `match` over it must carry a default — but there is no
longer anything to check: disagreement has become unrepresentable rather than
merely unlikely.

What that bought, precisely, is the length of the proof that the `case _` branch
is unreachable:

```text
before   isInvalid negates four predicates, one of which is isSymbol, whose
         seven comparisons must agree with seven hand-written `case`s written
         three functions away
after    isInvalid negates four predicates, one of which is
         symbolOf(c).isDefined, and the match IS symbolOf
```

Three steps down to one — which is what turns challenge 45's argument about that
branch from a question of risk into a question of principle.

### 47. `spanFrom` takes its predicate as `Char => Boolean`, and `Function1` is not specialised for `Char`, so every character is boxed and unboxed. Yet a 4,000,000-character scan allocates essentially nothing. Why? And is there a 4,000,000-character input for which that stops being true?

**"I don't know"**, then built from the primitive up. The bytecode is where it
starts, disassembled with `javap -c -p`:

```text
11: invokevirtual   String.charAt:(I)C
14: invokestatic    BoxesRunTime.boxToCharacter:(C)Ljava/lang/Character;
17: invokeinterface Function1.apply:(Ljava/lang/Object;)Ljava/lang/Object;
22: invokestatic    BoxesRunTime.unboxToBoolean:(Ljava/lang/Object;)Z
```

`boxToCharacter` is `Character.valueOf`, and `Character.valueOf` has a cache.
Measured by identity:

```text
Character.valueOf(code  97)   same instance on two calls?   true
Character.valueOf(code 126)                                 true
Character.valueOf(code 127)                                 true
Character.valueOf(code 128)                                 false
Character.valueOf(code 233)                                 false
```

The cache is **0 to 127** — exactly ASCII. It is the same mechanism as
`Integer.valueOf`'s −128..127 that Module 1 §19 measured, over a different
interval. The spec's inputs are ASCII throughout, so every box hits the cache and
returns an instance that already exists.

One `spanFrom` over 4,000,000 characters, and the boundary at one million
characters of a single code point each:

```text
all code  97 (ASCII)              16 bytes     code 126          16 bytes
all code 233 (non-ASCII)  64,000,016 bytes     code 127          16 bytes
                                               code 128  16,000,016 bytes
16.00 bytes per character                      code 129  16,000,016 bytes
```

The lone 16 bytes is the measurement's own tuple; the scan itself allocates
nothing. 16 bytes is a `Character`: a 12-byte object header plus a 2-byte `char`
field, aligned to 8.

**The input that reaches it was found unaided, and it is the finding.**
`isIdentifier` tests `c.isLetterOrDigit`, which delegates to
`Character.isLetterOrDigit` and is **Unicode-aware**. Guide §5 promises
*"letter or `_`, then letters, digits or `_`"*, promises nothing about Unicode,
and no test in `Stage1LexerSpec` supplies a character above 127. The lexer is
therefore **more permissive than its specification**, and that permissiveness is
the only door through which a non-ASCII character enters the grammar at all.

Measured end to end through `Lexer.tokenize`, on two 4,000,000-character
identifiers:

```text
all 'a'       (code  97)         272 bytes
all e-acute   (code 233)  64,000,352 bytes
delta                     64,000,080          ->  16.00 per character
```

Both are Latin-1 representable, so the `String` itself and the `substring` the
lexer takes cost the same in both runs: the delta is purely the boxing. The 272
bytes of the ASCII run carry a second finding worth keeping — `substring(0,
length)` returns `this` rather than a copy, so a single identifier spanning the
whole input allocates nothing at all.

**Not a defect, and not worth fixing.** 64 MB is transient young-generation churn
(Module 1 §6) on an input no test produces and the grammar does not promise.
What is worth having is the location of the cliff: a `Char => Boolean` parameter
costs zero for ASCII and 16 bytes per character above it, and the line is at code
point 127.
